## 目标与责任

完整目标保持为：P2P 空间配对、文本/图片/文件双向同步、加密历史与搜索、设备管理、同步控制、生命周期恢复、签名 Beta 和真机矩阵验收。
ArkUI 负责交互；一个 Runtime 负责 Engine 实例、事件消费和生命周期；Host 提供系统能力；Engine 唯一拥有加密、去重、配对、持久化、传输和重试规则。不能以 HTTP 兼容模式代替 P2P。

## 文件选取与句柄生命周期

本机官方 SDK 的 `@ohos.file.picker.d.ts` 提供带 UIAbilityContext 的 DocumentViewPicker，select 返回 URI 数组，maxSelectNumber 范围 1–500；save 接受 newFileNames。`@ohos.file.fs.d.ts` 提供 openSync、TRUNC、lseek、readSync/writeSync、fsyncSync 和 closeSync。Engine 的 HostFileAccess 使用不透明句柄，ExportEntry 在所有块写入后调用 finish_write，空文件也调用 finish_write。

方案：系统选择完成后打开文件，注册表在一次操作范围内持有 FD；输出经用户选择后只截断一次，完成时 fsync；最终由选取组件释放句柄。读写前用 lseek 到绝对偏移，避免 readSync 的相对偏移语义。URI 只用于打开文件，不持久化。放弃每块按 URI 重开的旧方案，因为它不能保持同一文件身份，也未处理覆盖后的旧尾部。

- [x] 系统选择/保存组件限定句柄有效范围，取消不执行操作，失败释放已打开文件。
- [x] 实际源码测试与 SDK 声明检查通过；新增文件/Picker 和文本分享用例，Host 共 44 项，会话加 Host 共 61 项。

DocumentPicker 已接入 Runtime 的 sendFiles/exportEntry 生命周期。退出时先阻止 Picker 新操作和晚到结果，再等待 Engine 关闭，最后 clear 文件注册表；不能在 Engine 尚在访问时释放所有 FD。每块按 URI 重开的旧逻辑已删除。

保存不是原子替换：系统提供的输出 URI 可能已创建或覆盖目标；中途失败必须显示失败，不能擅自删除用户选择的目标，也不能宣称旧内容得到保留。产品调用新版 Engine 文件接口仍等待经过校验的新 HAR。
